Coordinated Throughput Controller
=================================

Overview
--------

The Coordinated Throughput Controller is a custom Apache JMeter logic
controller built to solve a specific limitation of using multiple standard
Throughput Controllers as siblings.

With standard Throughput Controllers, each controller evaluates its own
percentage independently. For example, if two sibling Throughput Controllers
are both configured at 50%, both can evaluate to "run" during the same parent
iteration. That means a single thread/iteration can execute both branches.

The Coordinated Throughput Controller changes that behavior. Sibling
Coordinated Throughput Controllers under the same immediate parent controller
coordinate with each other and select only one coordinated child branch per
parent iteration. If the configured weights add up to less than 100, then some
parent iterations intentionally select no coordinated child.


Plugin Files
------------

The plugin jar is:

    lib/ext/jmeter-coordinated-throughput-controller-0.1.0.jar

The main runtime class is:

    org.apache.jmeter.control.CoordinatedThroughputController

The GUI class is:

    org.apache.jmeter.control.gui.CoordinatedThroughputControllerGui

In the JMeter UI, the controller appears as:

    Coordinated Throughput Controller


Installation
------------

1. Copy the jar into the target JMeter installation:

       <JMETER_HOME>/lib/ext/jmeter-coordinated-throughput-controller-0.1.0.jar

2. Restart JMeter.

3. Add the controller from the Logic Controller menu.

JMeter loads logic controller plugins at startup, so replacing the jar while
JMeter is already open is not enough. Restart JMeter after every plugin update.


Basic Usage
-----------

Place two or more Coordinated Throughput Controllers as sibling children under
the same parent controller, then place the samplers/controllers for each branch
inside the corresponding Coordinated Throughput Controller.

Example structure:

    Thread Group
      Loop Controller
        Transaction Controller
          Coordinated Throughput Controller - Login Flow
            HTTP Request - Login
            HTTP Request - Fetch Profile
          Coordinated Throughput Controller - Browse Flow
            HTTP Request - Browse Products
            HTTP Request - Product Details

If the first Coordinated Throughput Controller has weight 30 and the second has
weight 40, then across parent iterations:

    Login Flow  -> about 30%
    Browse Flow -> about 40%
    No branch   -> about 30%

Only one coordinated branch runs during a parent iteration.


Throughput Weight Field
-----------------------

The GUI field is:

    Throughput weight

This field accepts integer and decimal values, for example:

    40
    33.3
    1.5
    0

The value is interpreted as a weight. When the sum of sibling weights is less
than or equal to 100, the value also behaves like a percentage of parent
iterations.

Invalid non-numeric values are not recommended. If an invalid string is saved,
the runtime logs a warning and falls back to 100 for that controller.


How Selection Works
-------------------

The controller uses a deterministic balancing algorithm. It does not use random
selection.

For each parent iteration, all sibling Coordinated Throughput Controllers under
the same immediate parent register their weights. The shared group then chooses
one controller, or chooses no controller if the configured weights leave a
remainder below 100.

The algorithm keeps running balances for every branch and for the implicit
"no selection" branch. On each parent iteration:

1. Each controller's weight is added to its running balance.
2. If total configured weight is below 100, the remaining weight is added to
   the "no selection" balance.
3. The branch with the highest current balance is selected.
4. The selected branch has the round denominator subtracted from its balance.

This keeps the actual execution ratio close to the configured weights over
time, without random variation.


Behavior When Total Weight Equals 100
-------------------------------------

If sibling weights add up to exactly 100, exactly one coordinated controller
runs per parent iteration.

Example:

    Controller A: 50
    Controller B: 50

Across 10 parent iterations:

    A runs 5 times
    B runs 5 times
    No-selection runs 0 times

Only A or B runs during a given parent iteration. They do not both run in the
same iteration.


Behavior When Total Weight Is Below 100
---------------------------------------

If sibling weights add up to less than 100, the remaining percentage means
"run none of the coordinated children."

Example:

    Controller A: 30
    Controller B: 40
    Total:        70
    Remainder:    30

Across 10 parent iterations:

    A runs about 3 times
    B runs about 4 times
    No coordinated branch runs about 3 times

This is expected behavior. The controller does not normalize 30 and 40 to
roughly 43/57 because the total is below 100.


Behavior When Total Weight Is Above 100
---------------------------------------

If sibling weights add up to more than 100, the weights are treated as relative
weights and effectively normalize to 100%.

Example:

    Controller A: 60
    Controller B: 90
    Total:        150

There is no no-selection remainder because the total is above 100. The relative
split is:

    A: 60 / 150 = 40%
    B: 90 / 150 = 60%

Across 50 parent iterations:

    A runs about 20 times
    B runs about 30 times


Behavior With A Single Controller
---------------------------------

A single Coordinated Throughput Controller can be used alone. If its weight is
below 100, it runs only for its configured share and skips the rest.

Example:

    Controller A: 40

Across 100 parent iterations:

    A runs about 40 times
    No coordinated branch runs about 60 times

This fixes the earlier behavior where one controller at 40 could run for every
thread/iteration.


Decimal Weights
---------------

Decimal values are supported. They are not rounded before the decision is made.
The running-balance algorithm carries the fractional part across iterations.

Example:

    Controller A: 1.4
    Controller B: 1.5
    Controller C: 1.6

Total weight:

    1.4 + 1.5 + 1.6 = 4.5

Across 1000 parent iterations:

    A runs about 14 times
    B runs about 15 times
    C runs about 16 times
    No coordinated branch runs about 955 times

For very small test runs, the result is the nearest balanced whole-number
outcome, not a fractional execution. JMeter cannot run 0.4 of an iteration.

Example:

    1 thread
    Loop count: 6
    Weight: 48.3

Total parent iterations:

    1 * 6 = 6

Expected mathematical executions:

    6 * 48.3 / 100 = 2.898

The controller will run 3 times, not 2, because 3 out of 6 is closer to 48.3%
than 2 out of 6:

    2 / 6 = 33.33%
    3 / 6 = 50.00%

The controller chooses the closest balanced result over time rather than always
rounding down.


Threads, Loops, And Parent Iterations
-------------------------------------

The percentage applies to parent iterations, not directly to the number of
threads.

Total parent iterations are usually:

    number of threads * loop count

Examples:

    6 threads, loop count 1, weight 40
    Total parent iterations = 6
    Expected executions = 6 * 40 / 100 = 2.4
    Balanced result = about 2 executions

    6 threads, loop count 10, weight 40
    Total parent iterations = 60
    Expected executions = 60 * 40 / 100 = 24
    Balanced result = about 24 executions

Small totals can look slightly rounded because only whole iterations can run.
Larger totals become closer to the configured percentage.


Using Under A Transaction Controller
------------------------------------

The controller is intended to work under regular parent controllers, including
Transaction Controller.

Example:

    Transaction Controller
      Coordinated Throughput Controller 1, weight 30
        Debug Sampler - 30
      Coordinated Throughput Controller 2, weight 40
        Debug Sampler - 40

For 10 total parent iterations:

    Controller 1 runs 3 times
    Controller 2 runs 4 times
    No coordinated child runs 3 times

The Transaction Controller itself can still produce its own transaction sample,
depending on the Transaction Controller settings.


Copy/Paste Safety
-----------------

The plugin stores an internal branch id in the JMX:

    CoordinatedThroughputController.branchId

This id helps keep a branch stable across test execution. However, when a
controller is copied and pasted in the JMeter UI, the copied controller can
retain the same saved id.

The plugin handles this case at runtime. If sibling controllers register with
the same saved branch id during the same parent iteration, the plugin assigns
temporary unique runtime ids for that round. This prevents the first copied
controller from blocking the second copied controller.

You do not need to manually edit the branch id in the JMX.


Important Placement Rule
------------------------

Controllers coordinate only with sibling Coordinated Throughput Controllers
under the same immediate parent controller.

This works:

    Transaction Controller
      Coordinated Throughput Controller A
      Coordinated Throughput Controller B

This does not coordinate A and B with each other, because they are not siblings
under the same immediate parent:

    Transaction Controller
      Simple Controller 1
        Coordinated Throughput Controller A
      Simple Controller 2
        Coordinated Throughput Controller B

In the second example, each controller belongs to a different sibling group.


Zero And Negative Weights
-------------------------

Weights less than or equal to zero are treated as zero.

Example:

    Controller A: 0
    Controller B: 50

Controller A will not run. Controller B runs about 50% of parent iterations,
and no coordinated child runs about 50% of parent iterations.


NaN And Infinite Values
-----------------------

NaN and infinite numeric values are treated as zero by the runtime selection
logic.


Comparison With Standard Throughput Controller
----------------------------------------------

Standard Throughput Controller:

    - Each controller evaluates independently.
    - Multiple sibling throughput controllers can run in the same parent
      iteration.
    - Useful when independent gating is desired.

Coordinated Throughput Controller:

    - Sibling controllers evaluate as one coordinated group.
    - At most one sibling coordinated controller runs per parent iteration.
    - If total weight is below 100, some parent iterations run none.
    - If total weight is above 100, weights are treated relatively.
    - Useful for distributing threads/iterations across mutually exclusive
      test flows.


Recommended Use Cases
---------------------

Use this plugin when you want mutually exclusive traffic flows, for example:

    - 30% of users run login flow
    - 40% of users run browse flow
    - 20% of users run checkout flow
    - 10% of users do none of these coordinated flows

Or:

    - 50% of parent iterations run API group A
    - 50% of parent iterations run API group B
    - Never run both A and B in the same parent iteration


Practical Tips
--------------

1. Give parent controllers unique names when building complex plans. The plugin
   groups controllers by their immediate parent context.

2. Keep coordinated controllers as direct siblings when they should compete
   with each other.

3. If the total weight is less than 100, expect some threads/iterations to skip
   all coordinated children.

4. If you want every parent iteration to run exactly one coordinated branch,
   make the sibling weights add up to 100 or more.

5. Use more iterations for more accurate percentages. With very small thread or
   loop counts, exact percentages are impossible because executions are whole
   numbers.


Known Limitations
-----------------

1. The controller makes deterministic balanced decisions, not random decisions.
   This is usually better for repeatability, but it means the early sequence can
   look patterned.

2. Percentages are applied to parent iterations. If your test plan structure
   causes a parent to iterate differently than expected, the observed counts
   will follow the parent iteration count.

3. Very small tests can only approximate percentages. For example, 40% of 6
   iterations mathematically equals 2.4, but the controller can only run 2 or 3
   times.


Testing Performed
-----------------

The plugin has focused tests covering:

    - 50/50 sibling coordination
    - exactly one selected branch per parent iteration
    - one controller below 100
    - multiple controllers below 100 with no-selection remainder
    - total weight exactly 100
    - total weight above 100
    - decimal weights such as 1.4, 1.5, 1.6
    - zero weights
    - copied controllers with duplicate saved branch ids
    - usage under Transaction Controller
    - GUI label name

The focused test command is:

    ./gradlew :src:components:test --tests org.apache.jmeter.control.CoordinatedThroughputControllerTest -PchecksumIgnore
